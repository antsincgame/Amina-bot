## Фактор I — Амплификация вызовов: до ~16–20 внешних запросов на одно сообщение (HIGH)

Цепочка на обычное текстовое сообщение (без LM Studio):

1. **«Варп-гонка» 8 моделей** — `bot/src/ai/openrouter.ts:735-748` запускает
   `tryWarpRoutes` (4 Cerebras + 4 Groq **параллельно**, `openrouter.ts:212-265`)
   на КАЖДЫЙ chat-вызов до обращения к основной модели. Проигравшие отменяются
   после победителя, но запросы уже инициированы и расходуют RPM бесплатных тиров.
2. **Извлечение фактов памяти** — `memoryExtractor.extractFacts`
   (`bot/src/memory/user-memory.ts:632-682`) вызывает `aiService.complete(...)`
   на каждое сообщение ≥30 символов → **вторая полная гонка из 8 моделей**.
   `priority: 'background'` не передаётся — дроссель фоновых задач не работает.
3. **Верификатор** — `verifyResponse` может дёрнуть Perplexity (платный).
4. **enhanceResponseIfNeeded** — ещё один потенциальный web search.
5. **Автосуммаризация** — каждые N сообщений ещё один полный каскад.

Следствие: лимиты Groq/Cerebras выгорают, circuit breaker'ы открываются, ответы
деградируют к слабым моделям → «усталость» и падение качества личности.

**Протокол восстановления:**
- Гонку варп-маршрутов включать только как fallback при сбое основной модели
  (как и заявлено в комментарии «быстрый fallback до OpenRouter»), либо
  ограничить кандидатов до 2–3.
- `extractFacts`/`summarizeConversation` перевести на `priority: 'background'`
  + прямой дешёвый провайдер (одна модель Groq small), без каскада.

## Фактор II — Выбранная модель фактически игнорируется (HIGH, by design)

Даже при явном `ai_provider = 'openrouter'` и выбранной в админке модели шаг 1
(`openrouter.ts:737`) сначала гоняет Cerebras/Groq — настроенная модель OpenRouter
используется только если ОБА бесплатных провайдера упали. Качество ответа определяет
не выбор Магоса, а «кто из бесплатных ответил первым».

**Протокол:** при явном выборе провайдера в админке уважать выбор; варп-маршруты —
только после отказа выбранного.

## Фактор III — Гиперактивный веб-поиск подменяет личность (HIGH)

`REALTIME_PATTERNS` (`bot/src/ai/websearch.ts:213-291`) чрезмерно широки:
«расскажи про/о…», «что такое…», «кто такой…», «как работает…», фильмы, музыка,
книги, рецепты, здоровье… `text-handler.ts:179` направляет любое совпадение в
`handleDirectWebSearch` **до** основного пайплайна. Этот путь:

- собирает ответ из выдачи поиска **без памяти пользователя и без self-core**
  (`web-search-handler.ts:71` — только timeContext + данные из интернета);
- расходует платный поиск на каждый такой вопрос.

**Подтверждённый баг:** «расскажи о себе» матчится паттерном
`/расскажи\s*(про|о|об)\s/i` → Амина ищет в интернете информацию о самой себе,
а канон self-disclosure (`detectSelfDisclosureIntent`, fast-path в
`ai-pipeline.ts:334`) недостижим — перехват происходит раньше.

**Протокол:** проверять `detectSelfDisclosureIntent` ДО `handleDirectWebSearch`;
сузить паттерны прямого поиска до `FORCE_SEARCH_PATTERNS`-класса, остальное
оставить обычному пайплайну с `getSearchContext` (он и так подмешивает данные).

## Фактор IV — Анти-галлюцинационный контур воюет с правилами честности (MEDIUM)

`ACCURACY_RULES` (`bot/src/ai/persona.ts:195-201`) требуют: «если не знаешь —
прямо скажи». Но `SEARCH_REFUSAL_PATTERNS` (`bot/src/telegram/format.ts:497-567`)
трактуют именно такие формулировки («у меня нет актуальных данных», «рекомендую
проверить…») как отказ → `ai-pipeline.ts:100-112` запускает forceAnswer + Perplexity
и **заменяет честный ответ**. Получается петля: модель послушно честна → детектор
наказывает → лишние вызовы + несогласованность тона.

**Протокол:** не считать отказом честные ответы, когда поиск был недоступен/не
требовался; сверять reason с наличием `webSearchContext`.

## Фактор V — `isGibberish` стирает английские ответы из истории (LOW-MEDIUM)

`openrouter.ts:1120-1135`: при дефолтном `userLang='ru'` ответ длиннее 50 символов
с долей кириллицы <15% признаётся «мусором», и `ai-pipeline.ts:419` не сохраняет
его в историю. В англоязычном диалоге модель видит только вопросы без своих
ответов — контекст рвётся. Язык пользователя в функцию не передаётся нигде.

## Прочие подтверждённые/правдоподобные находки

- **Телефония:** дедупликация событий провайдера в памяти процесса — теряется при
  рестарте, возможна двойная обработка `call_completed`
  (`realtime-bridge-service.ts:288-323`); запуск realtime-сессии к media-bridge
  без ретраев (`realtime-runtime.ts:134-174`).
- **Новости:** DNS-lookup в `news-host-validation.ts:97-114` без явного таймаута;
  кэш валидированных хостов не выселяет протухшие записи (медленный рост);
  vibecoding-фильтр при сбое LLM-классификатора молча выбрасывает все
  «неоднозначные» заголовки (fail-closed без деградации к keyword-скорингу).
- **Дайджест:** `getTimeGreeting` (`digest-core.ts:464-472`) использует TZ процесса
  вместо `Intl` с настроенной зоной — расхождение возможно только если `TZ` env
  не совпадает с конфигом (low, консистентность).
- **Память-промпт:** «ОБЯЗАТЕЛЬНО используй имя пользователя в ответе»
  (`user-memory.ts:736`) на каждом ходу — имя в каждом ответе звучит неестественно.
- **Мелочи:** мёртвая ветка `voice` в `resolveCanonicalModelId`
  (`persona.ts:346-361`); Docker-сборка через `npm install` без lock-файла
  (невоспроизводимость); deprecation warning `punycode` в тестах.

# Литании исцеления — применено (этот PR)

Снятие перегрузки и устранение коллизий Техножрицы. Проверено: `tsc` (bot+admin)
чист, **1722/1722** тестов бота зелёные.

### Перегрузка маршрутизации (Факторы I/II) — `bot/src/ai/openrouter.ts`
- **Варп-гонка сокращена 8 → 2**: `tryWarpRoutes` берёт по одной флагманской модели
  Cerebras и Groq, а не весь список. Контекст: разведка варп-сети показала жёсткие
  лимиты — Groq 30 RPM / **1000 запросов в день на всю организацию**, OpenRouter
  free 20 RPM / 50 в день, причём **неудачные попытки тоже списываются**. Гонка 8
  моделей на каждое сообщение выжигала эти лимиты за часы.
- **Варп стал истинно аварийным**: упреждающая гонка осталась только в режиме `auto`.
  В явном `openrouter` выбранная Магосом модель идёт ПЕРВОЙ, варп — лишь fallback при
  её сбое (ШАГ 2.5). Это устраняет главную ложь админки (выбор модели игнорировался).
- **Happy-path**: при здоровой основной модели — 1 вызов вместо ~9.

### Коллизия идентичности (Фактор III) — `bot/src/telegram/handlers/text-handler.ts`
- Вопросы про саму Амину (`detectSelfDisclosureIntent`) больше НЕ уходят в веб-поиск:
  «расскажи о себе» шло в `handleDirectWebSearch` (паттерн `/расскажи (про|о|об)/`) —
  Амина искала саму себя в интернете вместо канона самораскрытия. Теперь идёт в
  fast-path персоны с памятью и self-core.

### Дросселирование фоновой памяти — `bot/src/memory/user-memory.ts`
- `extractFacts` и `summarizeConversation` помечены `priority: 'background'` —
  дросселируются при >50% бюджета провайдера, не воруют RPM у живого диалога.
  `aiService.complete()` теперь принимает `AIChatOptions`.

### Лечение ложного в админке
- `admin/src/pages/LMStudioPage.tsx`: подписи провайдеров приведены к правде.
  Раньше `cerebras` обещал «fallback → Groq» (Groq там НИКОГДА не пробуется),
  `auto` назывался «каскадным» (на деле параллельная гонка). Теперь честно.
- `admin/src/pages/SettingsPage.tsx`: описание моделей Cerebras/Groq исправлено
  (ссылалось на несуществующий «раздел AI Provider»); добавлен честный warning в
  карточку Chat Runtime Truth — в режиме «Auto» выбранная модель может не
  использоваться.
- `admin/tsconfig.json`: убран устаревший `baseUrl` — TypeScript 5.9.3 (зафиксирован
  в lock) превращал его в ошибку `TS5101` и **уже валил admin-typecheck в CI на main**.

### Намеренно НЕ тронуто в первом каскаде (закрыто во втором, см. ниже)
- Фактор IV, Фактор V, production-харднинг S1–S3.

# Литании исцеления — каскад II (боевая готовность на всех уровнях)

По прямому приказу Магоса «оптимизации боевой готовности на всех уровнях каскадом».
Проверено: `tsc` чист, **1722/1722** тестов зелёные.

### Безопасность — S1/S2/S3
- **S3 — `bot/src/telegram/webhook.ts`**: секрет Telegram-вебхука сравнивается
  `crypto.timingSafeEqual` с защитой по длине, а не `!==` (тайминг-атака закрыта).
- **S1 — `bot/src/features/telephony/lirax.ts`**: LiraX-вебхук стал **fail-closed в
  production** без токена (раньше — fail-open, любой мог подделать звонки). Аварийный
  выход для совместимости: `LIRAX_ALLOW_INSECURE_WEBHOOK=true` (env, без правки кода).
  В dev поведение прежнее. Задокументировано в `bot/.env.example`.
- **S2 — `bot/src/index.ts`**: при `TRUST_PROXY=true` в production пишется громкий
  warning о возможности подделки IP и обхода rate-limit (поведение не сломано —
  Магос сам выбирает точный hop-count под свою топологию Coolify/Cloudflare).

### Качество личности — Факторы IV/V
- **Фактор IV — `bot/src/telegram/handlers/ai-pipeline.ts`**: детектор отказов
  примирён с правилами честности. Честный «точно не знаю» на НЕ-поисковый вопрос
  больше не запускает forceAnswer + Perplexity и не перезаписывается — коррекция
  только когда поиск реально релевантен (`webSearchContext || needsWebSearch`).
- **Фактор V — `ai-pipeline.ts`**: язык пользователя из `telegram language_code`
  передаётся в `isGibberish` — английские ответы англоязычным больше не отбраковываются
  как «мусор» и не пропадают из истории. Без `language_code` — защита остаётся ('ru').

### Доведение искоренения варп-скверны
- **`bot/src/ai/openrouter.ts`**: гонка бесплатных моделей сокращена **7 → 3**
  (free-tier 20 RPM / 50 в день, неудачи списываются — 7 кандидатов выжигали лимит).
- **Фоновый бюджет в самой варп-гонке**: `tryWarpRoutes` принимает `priority` и
  пропускает Cerebras/Groq, если они за порогом фонового бюджета — фоновое извлечение
  фактов больше не ворует дефицитный free-RPM у живого диалога.

### Остаётся на отдельное решение Магоса (инфраструктура)
- Точное значение `TRUST_PROXY` под реальную цепочку прокси (Coolify? + Cloudflare?) —
  warning добавлен, но число хопов знает только Магос.

# Варп-аудит Ядра и Админки (4 Когитора) — итог верификации

По прямому приказу Магоса проведён глубокий агентский аудит четырьмя параллельными
Когиторами под надзором Fable: идентичность Ядра, мыслительный контур, правдивость
страниц Админки, целостность контракта Админка↔бэкенд. **Каждая находка
перепроверена лично по коду.** Ниже — что оказалось реальным, а что призраком.

### Реально исправлено
- **Дубли платного поиска** (`bot/src/ai/websearch.ts`): ключ in-flight дедупа не
  нормализовался — «Какой курс?» и «какой курс» запускали два одинаковых запроса.
  Ключ унифицирован с verify-кэшем. (единственный реальный дефект раунда.)

### Ложные тревоги (зафиксировано, чтобы не перепроверять снова)
- **`/api/stats` и `/api/status` «отсутствуют» (Delta, HIGH)** — НЕВЕРНО. Оба маршрута
  существуют в `bot/src/http/routes/stats.ts:8` и `health.ts:61`, смонтированы в
  `setup-routes.ts:54,49`. Дашборд получает реальные данные. Когитор искал только в
  `api/routes/` и не заглянул в `http/routes/`.
- **`lmstudio (not ready)` течёт в само-факты (Alpha, HIGH)** — НЕДОСТИЖИМО. Ярлык
  возникает только при `aiProvider=lmstudio && !hasLmStudio`, но enabled-факт чата
  требует `hasLmStudio=true` — условия взаимоисключающие. В disabled-факте
  используется `reason`, а не `provider`. Ложь в само-факт не попадает.
- **Статус-заглушка Админки `admin: ready:true` (Gamma, HIGH)** — защитима: срабатывает
  только при недоступном бэкенде, и admin-фронтенд в этот момент действительно жив.
  Реальный `/api/status` честно отдаёт `admin.ready = hasAdminDist`.
- **Ярлыки провайдеров «вводят в заблуждение» (Gamma, HIGH)** — уже исправлены в
  каскаде I; претензия основана на до-каскадной модели. После фикса в `auto` варп
  действительно идёт упреждающей параллельной гонкой флагманов — ярлык правдив.
- **Поле `elevenlabs_custom_voice_id` мёртвое (Gamma, MEDIUM)** — НЕВЕРНО. При
  сохранении (`useMultimodalSettings.ts:266`) оно пишется в `elevenlabs_voice_id`,
  который читает рантайм (`tts.ts:113`). Реестр честно помечает helper как `deprecated`.
- **Гейт детектора отказов (Beta, MEDIUM)** — Beta сам признал логику корректной;
  политические отказы на не-поисковый вопрос мы намеренно принимаем (не ломимся
  через границу). Действий не требует.

### Реальные, но низкого приоритета / by-design (оставлено)
- Амплификация вызовов на сообщение (Beta): после каскадов I–II happy-path = 1 вызов;
  оставшиеся (verify/extract/self-core) — намеренные слои честности, throttled.
- Edge-case supersede памяти и тихий сбой decay (Beta): редкие, не критичные.
- TTS `model`=voice-id для edge (Alpha, LOW): косметика.

**Вердикт Fable:** после двух каскадов исцеления Ядро Техножрицы и Админка
когерентны и честны. Варп-аудит не вскрыл скрытой скверны — лишь один микро-дефект
(дубли поиска), уже исцелённый. «Ложного», на что жаловался Магос, в коде больше
нет: оно жило в маршрутизации (выбор модели игнорировался) и ярлыках — закрыто
каскадом I.

# Опухоль памяти — найдена и удалена (каскад III)

Магос сообщил: «код теряет память, есть функция генерации логов, найдите её».
Два глубинных изучателя + личная построчная проверка Fable. Изучатели нашли
россыпь bounded-кэшей (которые на деле ограничены и НЕ текут), но **главную опухоль
пропустили** — её нашёл Fable лично.

### Реальная опухоль — удалена (transient-всплеск в сотни МБ)
Три функции-агрегатора накапливали **до 5000 ПОЛНЫХ документов в памяти ради
простого подсчёта по категориям**. Лог-документ — до 160 КБ (message ≤10КБ +
data ≤100КБ). 5000 × 160КБ ≈ **сотни МБ на один запрос статистики**, а дашборд
опрашивает их каждые 30с → устойчивое давление на память и OOM-рестарты.
- **`bot/src/config/db-logger.ts` `getLogStats`** — ТА САМАЯ «функция генерации
  логов». Переведена на потоковый подсчёт + `Query.select(['level','module'])`
  (не перекачивает тяжёлый data-блоб). Память: 5000 docs → 1 страница (100).
- **`bot/src/memory/user-memory.ts` `getEventStats`** — то же, `Query.select(['event_type'])`.
- **`bot/src/db/appwrite.ts` `analyticsRepo.getStats`** (путь дашборда `/api/stats`) —
  потоковая агрегация: в памяти только Set юзеров + карта токенов + счётчики, а не
  массив событий. Заодно `tokensByDay` через Map вместо `acc.find()` — было O(n²).
- **`db-logger` flush-таймер** теперь `.unref()` — не держит event loop.

### Переиспользование клиентов варп-маршрутов
- **`bot/src/ai/openrouter.ts`**: `tryWarpRoutes` создавал `new OpenAI(...)` на
  каждого кандидата на каждый запрос (2 клиента/сообщение с connection-пулами).
  Добавлен кэш клиентов по `baseURL+apiKey` — клиенты переиспользуются.

### Изучатели over-flagged (проверено: НЕ течёт)
- `memoryContextCache` (cap 200), `decayCounters` (clear >500), `verifyCache` (cap 50),
  `rateLimitStore` (cap 10000 + periodic unref-cleanup), `inflightSearches`/`per-key-mutex`
  (удаляются в finally) — **все ограничены**, это не утечки. Изучатель назвал их
  «HIGH unbounded», но caps на месте. Действий не требуют.

### Админка «прерывиста» — диагноз (на отдельный проход)
Корень «choppy»: агрессивный polling (dashboard/logs 30с, telephony 15–20с ×4
запроса) + отсутствие очистки `setTimeout` для тост-сообщений в нескольких страницах
+ невиртуализированные длинные списки (Users/Logs). Это реальная, но отдельная
правка по фронтенду (много мелких изменений по страницам) — выношу отдельным
каскадом, чтобы не смешивать с критичным лечением памяти Ядра. Память Ядра —
приоритет, она исцелена этим каскадом.

# Усмирение UI: зомби-процесс Self-Core (каскад IV)

Магос: «в Self-Core хаос, чувствую процессы-зомби и нестандартные баги». Прочитано
лично, построчно (без субагентов): `SelfCorePage.tsx` + `PersonaEditorSection.tsx`
+ `PromptLayersSection.tsx` + `AppwriteAuditPanel.tsx`.

### Зомби найден и убит — бесконечный цикл рендера
**`admin/src/components/self-core/PersonaEditorSection.tsx:119`** — `useEffect`
зависел от **всего объекта `props`**:
```js
useEffect(() => { props.onStateChange?.({ isDirty, isSaving }); }, [isDirty, props, ...]);
```
`props` — новый объект на каждом рендере → эффект срабатывал каждый рендер →
`setPersonaEditorState(новый объект-литерал)` в родителе → React видит новую ссылку →
ре-рендер → новый `props` → снова эффект. **Непрерывный цикл рендера**, грузивший CPU
и дававший «хаос» и «прерывистость» Self-Core. Исправлено: зависимость от стабильного
`onStateChange` (= `setState` из `useState` родителя), эффект теперь срабатывает только
при реальном изменении `isDirty`/`isSaving`.

### Тост-таймеры усмирены (Self-Core)
`showStatus` переведён на `useRef`-таймер: очищает предыдущий (быстрые статусы больше
не затирают друг друга) + cleanup при unmount + стабильная `useCallback`-ссылка (меньше
лишних рендеров дочерних). Дубль `setTimeout` в `createFact.onError` убран.

### Проверено и НЕ тронуто (не баги)
- Прочих циклов с зависимостью от всего `props` нет (греп): строка 117 использует
  стабильный `props.kernel` — безопасно.
- `setInterval` LMStudioPage уже корректен (`checkHealth` мемоизирован `[]`, есть
  `clearInterval`).
- Тост-таймеры на 6 других страницах безвредны: в React 18 setState-after-unmount —
  тихий no-op, не утечка. Намеренно не трогаю ради чистоты диффа.
- Polling (Telephony 4 запроса, Dashboard/Logs 30с) — осознанный live-update tradeoff,
  не баг.
